# 검증 규칙

주장을 증명할 수 있는 가장 작은 검증을 선택합니다.

## 기본 원칙

- 변경 성격과 가장 가까운 검증을 먼저 실행하고, 실패하면 원인을 확인한 뒤 더 넓은 검증으로 확장합니다.
- 테스트, lint, build가 모두 필요하지 않은 변경에는 관련 없는 검증을 완료 조건으로 만들지 않습니다.
- 반대로 UI·상호작용·전역 경계 변경은 명령 통과만으로 완료하지 않고, 필요한 화면 또는 브라우저 확인을 포함합니다.
- 명령은 기본적으로 변경 파일만 대상으로 실행합니다. 전체 lint·type-check·build는 아래 확장 조건이 있을 때만 실행합니다.

| 변경 범위                           | 기본 검증                                                                              | 확장 조건                                      |
| ----------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 문서·에이전트 설정                  | 변경 파일 확인, `pnpm exec prettier --check <변경 파일>`                               | 자동화 실행 방식이 바뀌면 관련 정적 확인       |
| 이슈 폼·GitHub Actions              | 변경 파일 확인, `pnpm exec prettier --check <변경 파일>`, 정적 매핑 확인               | 실제 GitHub 이벤트·권한은 CI에서 확인          |
| 단일 정적 화면·표현 컴포넌트·스타일 | 변경 TS/TSX의 `pnpm exec eslint --max-warnings=0 <변경 파일>`, 변경 파일 Prettier 검사 | props·export·import·타입을 바꾸면 type-check   |
| 디자인 기준이 있는 화면 구현        | 위 파일 단위 검사와 디자인 기준(Figma 등) 대비 화면 비교                               | 공통 경계 변경 시 type-check·build             |
| 타입·공개 API·import 경계           | 파일 단위 lint·Prettier, `pnpm type-check`                                             | route·layout·Provider 경계면 build             |
| 공통 layout·Provider·전역 스타일    | 파일 단위 lint·Prettier, `pnpm type-check`, `pnpm build`                               | 브라우저 동작이 있으면 화면 확인 추가          |
| 스크롤·반응형·인터랙션              | 관련 파일 검사와 데스크톱·모바일 수동 확인                                             | 상태 전이·타이머·observer가 있으면 테스트 검토 |
| Vitest 설정·단위 테스트             | 관련 `pnpm test:run <대상>`, `pnpm type-check`, 변경 파일 Prettier 검사                | 테스트 설정 전체 변경 시 전체 test:run         |

- `<변경 파일>`에는 공백으로 구분한 실제 수정 파일만 넣습니다. glob이나 저장소 전체 경로를 기본값으로 쓰지 않습니다.
- `pnpm lint`, `pnpm format:check`, 전체 `pnpm test:run`은 저장소 전체 검사가 필요한 확장 조건에서만 사용합니다.
- 검증은 비용이 낮고 실패 원인이 가까운 순서로 실행합니다. 예를 들어 표현 UI는 파일 단위 lint·format 후 화면을 확인하고, 전역 경계 변경은 type-check와 build까지 확장합니다.
- 최종 보고에는 변경 결과, 실행한 명령과 결과, 실행하지 못한 검증과 이유를 각각 남깁니다. 명령을 실행하지 않은 경우 통과라고 표현하지 않습니다.
- build 또는 브라우저 확인을 실행할 수 없으면, 이유와 남은 검증 공백을 명확히 보고합니다.
- GitHub Actions의 실제 권한, 이벤트 전달, branch protection 강제 여부는 로컬 검증 결과와 분리해 보고합니다.
- 회귀 위험이 큰 순수 로직·상태 전이를 추가하거나 바꾸면 `.claude/rules/testing.md`를 읽고 테스트를 함께 작성합니다.

## 자동 훅과 커밋 훅

- `lint-check.mjs`는 `Edit`·`Write` 이후 TS/TSX 파일 하나에 `pnpm exec eslint --quiet <파일>`을 실행하고, 오류가 있으면 결과를 에이전트에게 전달합니다. 편집은 이미 적용된 상태이므로 오류를 바로 수정하며, 이 검사가 완료 검증을 대신하지 않습니다.
- `pre-commit`의 `lint-staged`는 staged TS/TSX에 ESLint·Prettier를, staged JSON·CSS·Markdown·YAML에 Prettier를 실행하고 실패하면 커밋을 차단합니다. 아직 stage하지 않은 작업 파일은 검사하지 않습니다.
- 자동 훅은 빠른 피드백 경계이고, 작업자는 이 표의 변경 범위에 맞는 최소 수동 검증을 명시·실행합니다.

## 실패와 보고

- 실패한 명령은 성공한 다른 명령으로 덮지 않습니다. 실패 원인, 영향 범위, 재현 가능 여부, 다음 확인 항목을 분리해 남깁니다.
- 명령이 sandbox, 네트워크, 권한 같은 환경 제약으로 실패하면 코드 실패로 단정하지 않습니다. 실행 환경 제약과 코드 수준에서 확인한 근거를 함께 기록합니다.
- 최종 보고에는 변경 결과, 실행한 명령과 결과, 실행하지 못한 검증과 이유, 남은 위험을 순서대로 작성합니다.
