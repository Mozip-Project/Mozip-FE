# 현재 단체는 프론트가 단체 ID만 쿠키에 저장한다

- 상태: accepted
- 기록일: 2026-11-20

## 맥락

[017](./017-manage-posting-routes.md)에서 운영진 화면의 단체는 URL 대신 헤더에서 고른 값을 쿠키에 저장하기로 했지만, 쿠키를 누가 만들고 무엇을 담을지는 정하지 않았습니다. 처음에는 백엔드가 단체와 역할을 쿠키로 내려 주는 안을 논의했습니다. 운영진이 속한 단체 목록은 `me.memberships`로 받으며, 항목마다 역할(대표자·운영진), 단체, 팀이 함께 옵니다.

## 결정

- 헤더에서 단체를 고르면 프론트엔드가 자기 도메인 쿠키에 **단체 ID만** 저장합니다.
- 역할은 쿠키에 넣지 않고, `me.memberships`에서 쿠키의 단체 ID로 찾아 씁니다.
- 쿠키는 어느 단체 화면을 띄울지 정하는 용도로만 씁니다. 운영진 API는 지금처럼 `organizationId`를 인자로 받고, 백엔드가 요청마다 소속을 검사합니다.
- 쿠키가 없으면 소속 단체가 없을 때 지원자 홈(`/postings`), 있을 때 첫 번째 단체로 정합니다.

## 근거

- 단체 전환은 프론트엔드에서 시작하므로, 고르는 순간 프론트엔드가 저장하는 편이 흐름이 단순합니다.
- 프론트엔드 도메인 쿠키는 Next 서버(`proxy.ts`·layout)에서 바로 읽을 수 있어 화면을 고르는 데 추가 요청이 없습니다.
- 역할을 쿠키에 복제하지 않으면 역할이 바뀌었을 때 쿠키와 서버 값이 어긋나지 않습니다.
- 권한은 백엔드가 매 요청에서 확인하므로 쿠키 값을 바꿔도 다른 단체 데이터에 접근할 수 없습니다.

## 고려한 대안

- 백엔드가 단체·역할 쿠키 발급: 다른 기기에서도 마지막 단체를 유지할 수 있지만, 웹 서비스라 그럴 일이 적고 단체 전환마다 백엔드 요청이 필요합니다.
- 쿠키에 단체와 역할을 함께 저장: 역할이 `me.memberships`에 이미 있어 같은 값을 두 곳에서 관리하게 됩니다.

## 영향 범위

- 헤더 단체 선택(`components/ui/Gnb/organizationSelector.tsx`), 운영진 layout, 단체 ID를 인자로 받는 운영진 API
- 쿠키의 단체가 `me.memberships`에 없을 때(탈퇴, 같은 브라우저의 다른 계정)는 쿠키가 없을 때와 같은 기본값을 적용합니다.
- 확인 필요: 한 단체가 팀별로 `memberships`에 여러 번 올 수 있는지, 그때 역할이 다를 수 있는지, "첫 번째 단체"의 순서 기준
- 서버에서 `me.memberships`를 조회할 때의 로그인 쿠키 전달은 인증 작업에서 정합니다.
