# Next.js 성능

## 기본 경계

- App Router의 page와 layout은 Server Component를 기본으로 유지합니다. `'use client'`는 이벤트, state, effect, 브라우저 API가 필요한 가장 작은 경계에만 둡니다.
- Client Component가 import하는 모듈은 client bundle에 포함됩니다. 큰 화면이나 페이지 전체에 지시문을 두지 않습니다.
- Provider는 필요한 만큼 트리의 깊은 위치에 둡니다. 전역 상태가 필요 없는 정적 화면을 Provider로 감싸지 않습니다.

## 자산과 외부 코드

- 폰트는 `next/font`(`local` 또는 `google`)로 로드합니다. `public/`의 수동 `@font-face`나 외부 CSS 링크로 런타임 폰트 요청을 만들지 않습니다. 사용할 서체는 디자인 시스템이 정해지면 결정합니다.
- 정보성 래스터 이미지는 `next/image`를 우선 사용하고, 크기 또는 비율·`sizes`를 명시합니다. `priority`는 LCP 후보 이미지에만 사용합니다.
- `<video poster>`, 순수 `<img src>`처럼 `next/image`를 거치지 않는 경로는 배포 환경에서도 자동 최적화되지 않습니다. 이런 경로에 쓰는 원본 파일은 미리 압축·WebP 변환해서 커밋합니다.
- 무거운 브라우저 전용 기능과 제3자 스크립트는 사용자 가치와 측정 근거가 있을 때만 지연 로드합니다. 초기 화면에 필요 없는 분석·위젯은 초기 렌더링을 막지 않아야 합니다.

## 상호작용과 렌더링

- 스크롤·터치 리스너는 섹션마다 중복 등록하지 않고, 가능하면 passive listener를 사용합니다.
- 스크롤 모션은 `transform`과 `opacity`를 우선하고, 매 프레임 레이아웃 측정·대형 DOM 갱신을 하지 않습니다.
- 단순한 계산에 `useMemo`를 남용하지 않습니다. 파생 상태는 렌더링 중 계산하고, 렌더링에 반영하지 않는 잦은 값은 `useRef`를 검토합니다.
- 성능 최적화는 실제 병목, 큰 자산, 또는 사용자 체감 문제가 확인됐을 때 적용합니다. 추측성 dynamic import·메모이제이션을 기본값으로 두지 않습니다.

## 변경 전 확인 질문

- 이 `'use client'` 지시문이 더 안쪽 상호작용 컴포넌트로 내려갈 수 있는가?
- 이 이미지가 첫 화면의 LCP 후보인가? 아니라면 `priority`가 정말 필요한가?
- 화면 밖 기능·스크립트가 초기 렌더링과 같은 시점에 내려받아지고 있지 않은가?
- 목록·테이블처럼 항목이 많은 화면에서 불필요한 재렌더링이나 한 번에 너무 많은 DOM을 그리고 있지 않은가?
