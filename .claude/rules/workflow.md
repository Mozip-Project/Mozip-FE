# 작업 흐름

1. 변경 성격을 구분하고 현재 구현과 필요한 지침을 확인합니다. 디자인 변경일 때만 디자인 기준 자료(Figma 등)를 추가로 읽습니다.
2. 현재 작업 트리의 사용자 변경과 관련 파일을 확인하고, 보호해야 할 기존 동작을 짧게 정의합니다.
3. 가장 작은 검증 가능한 성공 기준을 정합니다.
4. 필요한 파일만 수정합니다. 새 공용 경계·의존성·자동화 계약이 필요하면 먼저 기존 패턴과 대안을 확인합니다.
5. 변경된 UI는 데스크톱과 모바일 기준에서 확인합니다.
6. 가장 구체적인 검증을 실행하고 결과와 공백을 보고합니다.

## 변경 유형별 기준

### 화면과 스타일

- 요구사항과 디자인 기준(있으면)을 먼저 확인하고, 해당 화면 안에서 구현합니다.
- 화면 조립과 하위 마크업·상호작용을 분리하되, 한 번만 쓰는 코드까지 공용화하지 않습니다.
- 반응형, 이미지 비율, heading 구조, CTA 목적을 확인합니다.

### 상호작용과 모션

- browser API, observer, timer, scroll 상태가 필요한 가장 작은 Client Component를 찾습니다.
- cleanup, reduced motion, 키보드·터치 흐름을 함께 검토합니다.
- 상태 전이 또는 반복 상호작용이 있으면 테스트 추가 필요성을 판단합니다.

### 설정과 문서

- 설정 변경은 로컬 명령, CI, 배포 build에 미치는 영향을 확인합니다.
- workflow·이슈 양식 변경은 이벤트, 권한, 파싱 section, branch·label·title 매핑을 함께 검토합니다.
- 문서에는 현재 존재하는 명령, 디렉터리, 자동화만 작성합니다.

### 리팩터링

- 기능 변경과 구조 변경을 한 diff에 섞지 않습니다.
- 수정 전후 유지해야 하는 화면·상호작용을 정하고, 그 결과를 증명할 최소 검증을 실행합니다.
- 새 레이어 추가보다 기존 구조의 삭제, 이동, 재사용을 우선합니다.

## 변경 통제

- 확정되지 않은 사업·제품 사실을 추가하기 전에 근거를 요청합니다.
- 구조·라이브러리·공통 규칙처럼 반복 영향을 주는 결정은 `.claude/decisions/README.md`를 확인해 짧게 기록합니다.
- 제공 자료, 외부 서비스, 브라우저 동작처럼 코드만으로 해소할 수 없는 막힘은 `.claude/known-issues/README.md`에 기록할지 검토합니다.
- 문서·명령·workflow가 실제 구현과 어긋나면, 같은 변경에서 맞춰 갱신합니다. 다만 단순 작업 로그를 decision이나 known issue로 남기지 않습니다.
