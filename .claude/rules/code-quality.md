# 구현 품질 기준

코드는 다음 작업자가 특정 구간을 바꾸더라도 다른 구간의 의도와 동작을 쉽게 파악하고 안전하게 수정할 수 있어야 합니다.

## 네 가지 판단 기준

- **가독성**: 한 파일에서 동시에 이해해야 할 맥락을 줄이고, 위에서 아래로 코드의 의도가 읽히게 합니다.
- **예측 가능성**: 이름과 props(또는 인자)만으로 어떤 상태·동작을 기대할 수 있는지 드러냅니다.
- **응집도**: 함께 수정되는 마크업·데이터·상호작용·타입은 가까이에 둡니다.
- **낮은 결합도**: 단순히 모양이 비슷하다는 이유로 서로 다른 기능의 변경 시점을 묶지 않습니다.

가독성과 공통화가 충돌하면, 실제로 함께 변경되는지와 동기화 실패 위험을 기준으로 판단합니다. 일회성 중복은 허용하지만, 같은 규칙을 여러 곳에서 동시에 수정해야 하면 공통 경계를 검토합니다.

## 구현 전 판단

- 요구사항, 기존 코드로 확인할 수 있는 사실과 아직 결정되지 않은 사항을 구분합니다.
- 해석이 여러 개여도 화면 구조·동작에 영향을 주지 않으면 가장 단순하고 되돌리기 쉬운 선택을 합니다.
- 해석에 따라 사용자 흐름, 외부 연결, 새 의존성이 달라지면 추측으로 구현하지 않고 근거 또는 결정을 확인합니다.
- 성공 기준은 "예쁘게 구현"이 아니라 기능·반응형·접근성·검증처럼 확인 가능한 결과로 정합니다.
- 기존 동작을 바꾸지 않는 정리라면 먼저 유지해야 할 결과와 최소 검증을 정하고, 기능 변경과 같은 diff에 섞지 않습니다.

## 기능 단위로 변경 경계를 유지하기

- `page.tsx`는 화면 구성 요소의 순서와 조합만 보여줍니다. 한 화면에서만 쓰이는 마크업·데이터·타입·작은 상호작용은 그 화면 가까이에 둡니다.
- 다른 화면에서도 같은 목적과 변경 주기를 공유할 때만 공용 컴포넌트나 상수로 올립니다. 단지 비슷해 보인다는 이유로 합치지 않습니다.
- 한 파일이 화면 구성, 데이터 관찰, 데이터 변환, 상태 관리를 모두 맡기 시작하면 사용자에게 보이는 단위 또는 동작 단위로 나눕니다.

## 의도를 코드에 남기기

- 조건이 길어지면 결과를 설명하는 이름을 붙입니다. 읽는 사람이 JSX에 도달하기 전에 왜 보이거나 숨겨지는지 알 수 있어야 합니다.
- UI를 그리는 코드와 데이터 변환·브라우저 제어가 한 파일에서 서로 읽기 어려워지면, 사용자에게 보이는 단위와 동작 단위를 따라 분리합니다. 정적 화면에 API·상태 레이어를 미리 만들지는 않습니다.
- 시간·지연·횟수·화면 기준점처럼 조정 가능한 값은 의미와 단위가 드러나는 상수로 선언합니다.
- 함수와 이벤트 핸들러는 한 가지 사용자 결과를 책임집니다. 추적, 화면 이동, 상태 변경처럼 서로 다른 결과가 함께 발생하면 이름 또는 호출 위치에서 각각을 드러냅니다.
- 중첩 삼항 연산자와 지나치게 먼 선언·사용 위치를 피합니다. 짧은 JSX 조건은 유지하되, 여러 경우의 수는 읽는 흐름을 우선해 분기합니다.
- 매직 넘버는 시간·거리·개수·임계값처럼 조정 의미가 있을 때 상수로 올리고, 이름에 단위(`_MS`, `_PX`)를 드러냅니다. 자명한 0·1 또는 단발성 스타일 값까지 기계적으로 상수화하지 않습니다.

## 상태와 브라우저 코드를 격리하기

- 정적 콘텐츠에는 state와 effect를 추가하지 않습니다. 화면에서 계산할 수 있는 값은 별도 state로 복제하지 않습니다.
- 브라우저 API, 이벤트, 애니메이션 상태가 필요한 부분만 Client Component로 분리합니다. 상위 화면 전체를 client화하지 않습니다.
- Context나 Provider는 서로 떨어진 화면이 같은 상태를 실제로 변경·구독할 때만 도입합니다. 전달 경로가 짧고 역할이 분명한 props는 유지합니다.

## 변경 전에 확인할 질문

- 이 파일을 처음 보는 사람이 담당하는 구간과 변경 이유를 빠르게 알 수 있는가?
- 이 변경으로 같이 확인해야 하는 화면과 공통 코드의 범위가 필요한 만큼으로 제한되는가?
- 작은 중복을 제거하려다 서로 다른 화면의 수정 시점을 묶고 있지 않은가?
- 반응형·접근성·성능을 해치지 않고도 같은 결과를 더 단순하게 표현할 수 있는가?

## 변경 통제

- 요청 해결에 필요한 파일과 줄만 수정합니다. 무관한 dead code나 리팩터링 후보는 삭제하지 말고 별도로 언급합니다.
- 새 상태·Provider·의존성·공통 컴포넌트를 도입할 때는 기존 props, 지역 상태, HTML/CSS 조합으로 해결할 수 없는 이유가 있어야 합니다.
- 변경으로 더 이상 쓰이지 않는 import·변수·함수만 같은 diff에서 정리합니다.

TypeScript의 `any`와 근거 없는 type assertion은 사용하지 않습니다. 접근성 또는 반응형 동작을 희생해 시각적 결과만 맞추지 않습니다.
