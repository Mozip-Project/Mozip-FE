# 프로젝트 구조

> 초안입니다. **확정**은 MOZIP 성격상 거의 무조건 필요한 기준이고, **회의 안건**은 팀이 함께 정할 항목입니다. 회의에서 결정하면 안건을 확정 쪽으로 옮기고, 그때 실제 폴더를 만듭니다.

## MOZIP 구조에 영향을 주는 특징

- **사용자가 두 종류**: 지원자와 운영진은 화면, 레이아웃, 권한이 다릅니다.
- **양쪽이 같은 데이터를 씁니다**: 공고, 지원서, 면접 데이터가 지원자 화면과 운영진 화면에 모두 나옵니다.
- **API 중심**: 대부분의 화면이 백엔드 데이터를 다루고, AI 기능도 API로 받습니다.
- **무거운 폼과 인터랙션**: 지원서 작성, 문항 설정, 캘린더, 면접표, 실시간 면접 보드가 있습니다.

## 확정

### 1. `app/`은 라우팅만 담당합니다

`page.tsx`는 화면에 무엇을 어떤 순서로 둘지만 정합니다. API 호출, 비즈니스 로직, 큰 UI 덩어리는 `app/` 밖에 둡니다. 그 화면에서만 쓰는 작은 UI는 옆에 `_components/`를 두어도 됩니다. `_`로 시작하는 폴더는 URL에 포함되지 않습니다.

### 2. 영역을 지원자, 운영진, 인증으로 나눕니다

```text
src/app/
├── layout.tsx       # html·body, 전역 폰트·스타일·Provider
├── (auth)/          # 로그인·회원가입
├── (applicant)/     # 지원자 영역 (지원자용 레이아웃)
└── <운영진 경로>/   # 운영진 영역 (운영진용 레이아웃, 인증 필요)
```

괄호로 감싼 폴더(route group)는 URL에 포함되지 않습니다. 영역마다 `layout.tsx`를 따로 두어 헤더, 네비게이션, 권한 처리를 분리합니다.

### 3. API 호출은 한 곳의 클라이언트를 거칩니다

base URL, 인증 토큰, 에러 처리를 컴포넌트마다 따로 작성하지 않고, 공용 API 클라이언트 하나를 통해 호출합니다.

### 4. 공용 코드는 도메인을 모릅니다

Button, Modal 같은 기본 UI와 날짜 포맷 같은 유틸은 "공고"나 "지원서"를 몰라야 합니다. 도메인 코드가 공용 코드를 가져다 쓰고, 그 반대는 하지 않습니다.

### 5. 라이브러리 (2026-10-15 FE 회의)

| 영역        | 결정                  | 사용 기준                                                                    |
| ----------- | --------------------- | ---------------------------------------------------------------------------- |
| 기본 UI     | shadcn/ui             | 컴포넌트 코드를 저장소에 복사해 디자인 시스템에 맞게 수정                    |
| 서버 상태   | TanStack Query        | 브라우저에서 서버 데이터를 읽고 쓰는 화면. 공개 조회는 Server Component 우선 |
| 전역 상태   | 도입하지 않음         | 서버 데이터는 Query 캐시, 화면 간 공유 값은 URL·props 우선. 필요해지면 검토  |
| 폼과 검증   | react-hook-form + zod | 지원서·문항 설정처럼 입력과 검증이 있는 화면                                 |
| HTTP        | ky                    | 공용 API 클라이언트 한 곳에서만 사용                                         |
| 실시간 갱신 | 폴링                  | 면접 보드처럼 다른 사람의 변경을 봐야 하는 화면. 방식 변경은 백엔드와 결정   |
| UI 문서     | Storybook             | 공용 UI와 핵심 도메인 컴포넌트                                               |
| API 목킹    | MSW는 필요해지면 도입 | 백엔드 API가 없어 개발이 막힐 때 검토                                        |

설치는 각 라이브러리를 처음 실제로 쓰는 작업에서 합니다.

### 6. 인증 토큰은 httpOnly 쿠키로 받습니다

백엔드가 토큰을 httpOnly 쿠키로 발급하고, 프론트엔드 코드는 토큰을 직접 읽거나 저장하지 않습니다. 쿠키가 정상적으로 오가려면 FE와 BE가 같은 사이트(예: `mozip.kr`, `api.mozip.kr`)로 배포되어야 합니다. 로컬(`localhost`)에서는 이 조건이 드러나지 않으므로 배포 환경에서 따로 확인합니다.

## 회의 안건

### A. 도메인 코드를 어디에, 어떻게 둘까

공고, 지원서처럼 여러 화면이 함께 쓰는 코드(API 함수, 타입, 도메인 컴포넌트)를 어디에 둘지 정합니다.

| 선택지        | 예시                                      | 장점                          | 단점                              |
| ------------- | ----------------------------------------- | ----------------------------- | --------------------------------- |
| 도메인별 폴더 | `features/recruit/{api,components,hooks}` | 공고 관련 코드가 한곳에 모임  | 처음 규칙을 익혀야 함             |
| 종류별 폴더   | `apis/`, `components/`, `hooks/`          | 직관적이고 시작이 쉬움        | 커지면 한 폴더에 파일이 많이 쌓임 |
| FSD           | `entities/`, `features/`, `widgets/`      | 규칙이 엄격해서 일관성이 높음 | 층이 많아 학습·세팅 비용이 큼     |

초안 추천은 **도메인별 폴더**입니다. 양쪽 역할이 같은 데이터를 쓰는 MOZIP에 잘 맞습니다.

### B. 도메인 이름

백엔드 API, 엔티티 이름과 맞추는 것이 좋습니다. 임시 이름은 다음과 같습니다.

- `recruit`: 공고
- `application`: 지원서·문항
- `interview`: 면접 일정·운영
- `evaluation`: 평가
- `profile`: 프로필·활동 경험·답변 아카이브
- `auth`: 인증

### C. URL 설계

- 운영진 경로: `/manage` 또는 `/admin`. 백엔드 쪽 서비스 관리자 페이지와 헷갈리지 않게 `/manage`를 제안합니다.
- 운영진이 여러 조직(동아리·학회)을 관리할 수 있는지 정합니다. 가능하다면 `/manage/[orgId]/...`처럼 조직 ID가 URL에 들어갑니다.
- 지원자 메인(`/`)을 공고 탐색 화면으로 쓸지, 소개 화면을 따로 둘지 정합니다.

### D. 계정 구분

토큰 저장 방식은 확정 6번(httpOnly 쿠키)으로 정했습니다. 지원자와 운영진 계정을 어떻게 구분할지는 백엔드·기획과 함께 정합니다. 결정 결과에 따라 `app/api/`(Route Handler)나 `proxy.ts`(Next.js 16에서 `middleware` 대신 사용)가 필요한지가 달라집니다.

## 공통 원칙

- 기본은 Server Component로 작성하고, 클릭·입력·브라우저 API가 필요한 부분만 `'use client'`로 분리합니다.
- 두 화면 이상에서 같은 이유로 바뀌는 코드만 공용으로 올립니다. 모양이 비슷하다는 이유만으로 미리 묶지 않습니다.
- `loading.tsx`, `error.tsx`, `not-found.tsx`는 실제로 필요한 화면이 생길 때 추가합니다.
